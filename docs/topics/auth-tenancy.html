Liverty Music 仕様ガイド ／ 認証とテナンシー

認証とテナンシー：
誰が、どこから入り、何が見えるか

Liverty Music の利用者は 3 種類います。ファン、Organizer (チケットを売る事業者) のメンバー、社内の管理者です。この文書は、それぞれがどう登録・ログインし、どこまでのデータを見られるか、そしてパスキーを失ったときにどう戻るかを 1 枚にまとめたものです。サインインはすべて Zitadel (外部の identity provider) が受け持ちます。

  1. 3 種類の利用者は、Zitadel の別々の Organization に住む

    ファンは liverty-music、管理者は admin、Organizer は 1 社ごとに専用の Organization。同じメールでも Organization が違えば別のアカウントで、片方からもう片方へは入れません。

  2. パスワードはない。パスキーを失ったときの戻り方は利用者ごとに違う

    ファンは確認済みメールに届くリンクで自分で再登録、Organizer のメンバーは管理者の再招待、管理者は Google Workspace のアカウントで入ります。

  3. 「誰のデータか」はリクエストではなくトークンが決める

    ファン向け API のリクエストは User id を持ちません。Organizer 向け API はトークンの Organization から自社の Organizer を引きます。URL の値は権限になりません。

1. 全体図：3 本のレーンは交わらない

3. ファンの登録とログイン ファン

登録もログインも、ファンが自分で押したボタンからしか始まりません (Timetable のバナー、Concert ページ、Settings など)。閉じられないモーダルで登録を迫ることはしません。登録とログインは同じ流れで、戻ってきたあと fan app が必ず UserUseCase.Create を呼びます。Create は新しい identity なら User を作り、登録済みなら既存の User をそのまま返します。

User はどう決まるか

1 つの User は Zitadel の identity 1 つ (provider user ID) にひも付きます。fan app は「この identity の User はこれ」と端末で覚え、サインアウトで忘れます。忘れたあとは次のサインインでまた Create を呼びます。Create がメールとして保存するのはトークンの identity のメールで、リクエストに書かれたメールは使いません。別の identity が同じメール (大文字小文字を区別しない) を使っていれば Create は AlreadyExists になりますが、fan app はエラーを記録するだけで、ファンはそのままアプリを使えます。

起動のたびに、fan app はほかの個人向けリクエストより先に UserUseCase.Get で User を読み直します。表示言語は User の preferred language が勝ち、端末が覚えていた言語は捨てます。ホームが未設定なら、登録時ではなく次に Timetable か My Artists を開いたときに聞きます。

4. ログイン状態の維持 ファン

トークンの寿命は Zitadel のインスタンス全体の設定で、コード (IaC) に固定されています。アクセストークンを短くして漏れたときの被害を小さくし、リフレッシュトークンを長くしてファンがログインし直さずに済むようにしています。

fan app はトークンをタイマーで更新しません。Zitadel はリフレッシュトークンを使うたびに新しいものへ替える (rotation) ため、タイマーとサービスワーカーによる再読み込みが重なると同じトークンを 2 回使い、強制ログアウトになるからです。代わりに次の 3 つの時点で更新します。

5. パスキーとメール確認と復旧 ファン

ファンのサインイン手段はパスキーだけです。だから「パスキーを全部失ったら戻れない」状態を作らないことが、この節の目的です。戻り道は確認済みのメールアドレス 1 本なので、メール確認がその前提になります。

メール確認

新しい User ができると、User の表示言語で確認メールが届きます。リンクは 1 時間有効で、どの端末で開いてもサインインなしで確認できます。ただしリンクを開いただけでは確認されません。画面に出る「メールアドレスを確認する」ボタンを押したときだけ確認され、メールを自動で開くセキュリティソフトが勝手に確認してしまうことを防いでいます。期限切れや使用済みのリンクは拒否され、Settings から送り直せます (1 人あたり 10 分に 3 回まで)。確認リンクの検証は、送信元ごとに 60 分 10 回、同じ User id に 60 分 5 回までです。存在しない User と間違ったコードは同じエラーになり、User がいるかどうかは分かりません。

パスキーを全部失ったとき

パスキーの管理

Settings のパスキー管理で、一覧・追加・削除ができます。別の端末 (例: スマホのパスキーで QR を読んでサインインした Windows ノート PC) に追加するには、直近 5 分以内にサインインしている必要があります。同じパスキー提供元に 2 つ目は作りません。最後の 1 つは削除できません。追加も削除もメールで知らせ、身に覚えのない追加なら削除するよう促します。

パスキーの正本は Zitadel です。Liverty Music の Passkey は「どの提供元で、いつ登録したか」を表示するための記録で、Zitadel からの webhook で作られます。パスキー管理の画面は、Zitadel が持つパスキーを一覧にし、この記録を id で突き合わせて提供元名と登録日を足します。記録が無いパスキー (記録を始める前に作ったもの、通知が届かなかったもの) も一覧に出ますが、名前だけで日付はありません。

6. Organizer の作成と初回ログイン Organizer

Organizer は管理者が作ります。作ること自体が審査の結果です。作成と同時に、その Organizer 専用の Organization が Zitadel にでき、オーナーの identity (パスワードなし、メール確認済み) と招待メールが用意されます。オーナーが行動するのは招待メール 1 通だけです。

Organizer の状態と、メンバーへの応答

7. Organizer の 2 回目以降のログイン Organizer

organizer console は 1 つの OIDC クライアント (organizer-console) ですべての Organizer を受け持ちます。だから console は、サインインを始める前に「どの Organization か」を必ず 1 つに決めます。決めないまま始めると、同じメールのファンのアカウントに一致してしまうからです。

ファンのアカウントと同じメールで Organizer を運営する人は、fan app ではファンのパスキーで、console では Organizer のパスキーでサインインします。どちらも入力するのは同じメールだけです。ログイン画面には <メール> (xx-records) のように Organizer の short name が表示されます。

8. 管理者 管理者

admin console は fan app とは別のアプリです。サインイン要求に admin の Organization の id を urn:zitadel:iam:org:id:<id> スコープで入れることで、Zitadel にファン用ではなく admin のログインポリシー (Google Workspace の IdP) を使わせます。Google Workspace のサインインを通れることが、そのまま入口の条件です。認証コールバック以外のすべての画面はログイン必須で、未ログインならどの画面も表示する前にサインインへ送ります。

admin console API は、リクエストごとに有効なトークンと admin 役割を確かめます。Organizer の作成・停止・削除や、ファンの削除はここからしかできません。

9. 他人・他社のデータに入れない仕組み

API はリクエストを読む前に、上から順に関門を通します。どこかで落ちたリクエストは何も変えません。どの API でもトークン (JWT) は Zitadel の公開鍵で検証します。

fan API

  1. 有効なトークンかいいえ → Unauthenticated
  2. トークンの identity から User を引く (ResolveCaller)User が無い → NotFound
  3. リクエストは User id を持たないいつも呼び出した本人の User だけを読み書きする

例外: RequestPasskeyRecovery と VerifyEmail はトークンなしで受ける (サインインできない人のため)。代わりに送信元ごとに 60 分 10 回まで。

organizer API

  1. 有効なトークンかいいえ → Unauthenticated
  2. organizer console 向けに発行され、役割のある Organization がちょうど 1 つかいいえ → PermissionDenied
  3. Organization から Organizer を引く (ResolveCaller)無い・provisioning → PermissionDenied
    deactivated → FailedPrecondition
  4. 引けた Organizer のためだけに動く他社の Organizer を指す方法がない

console の画面側でも owner 役割を確かめ、別の Organizer の URL を開くと「別の Organizer のアドレス」と表示してデータを出さない。最終判断は API。

admin console API

  1. 有効なトークンかいいえ → Unauthenticated
  2. admin 役割があるかいいえ → PermissionDenied
  3. 管理操作Organizer の作成・停止・削除、ファンの検索・削除

Zitadel のアカウントを変えられるのは identity service だけ

Zitadel の管理 API の資格情報を持つのは、バックエンドの identity service という 1 つのプロセスだけです。クラスタの外からは届かず、呼び出し元ごとに頼める操作が決まっています。外部のデータを処理する API サーバーやイベント処理が乗っ取られても、ファンのアカウントや Organizer の Organization を書き換えられないようにするためです。

呼び出し元identity service に頼める操作
fan API確認メールのコードでアドレスを確認済みにする／退会するファン本人の identity を削除する。これ以外は拒否
イベント処理 (event consumer)確認コードの発行／パスキー登録リンクの発行
admin console APIファンの identity の削除／Organizer の Organization の作成・Provision・停止・削除
それ以外 (organizer API など)届かない

Zitadel からバックエンドへの webhook は 3 つあり、どれもクラスタ内からしか受けず、署名の無いものは 401 で拒否します。1 つはサインインの通知 (login-events) で、対話的なサインインの時刻を User に記録します。1 つはパスキーの追加・削除の通知 (passkey-events) で、ファンの Organization の分だけ記録します。もう 1 つ (pre-access-token) はアクセストークンの発行直前に呼ばれ、メールが確認済みなら email クレームを足します。決済の通知 (payment-events) は Stripe からで、別の webhook です。

10. 取り違えやすい点

取り違え正しくは取り違えると
User と identity は同じものUser は Liverty Music の DB の行、identity は Zitadel のアカウント。provider user ID で 1 対 1 にひも付くidentity だけ消して User が残る、またはその逆の不整合を作る。退会は identity を先に消し、次に User を消す
Organization と Organizer は同じものOrganization は Zitadel のサインインの単位で DB に行がない。Organizer は事業者で DB にある。provider organizer ID でつながるOrganizer の停止で Organization も消えると思い込む。停止では identity が止まるだけで Organization は残る
同じメールなら同じ人のアカウントOrganization が違えば別の identity・別のパスキー。どちらからも他方へは入れないファンのアカウントで Organizer の画面に入れる穴を作る。console が Organization を指定せずにサインインを始めると、ファンのアカウントに一致する
URL の ?org= や ?org_id= で Organizer が決まる決めるのはトークンの Organization。URL はログイン画面を選ぶ目印だけURL を書き換えるだけで他社のデータが見える
メール確認はおまけパスキー復旧のリンクは確認済みのアドレスにしか送らない未確認のファンはパスキーを失うと戻れない。しかも画面は誰にでも同じ答えなので、本人は送られないことに気付けない
「該当なし」を知らせないのはバグパスキー復旧と Organizer のリンク送信は、アドレスの有無で答えも時間も変えない仕様「このメールは未登録です」と出すと、誰が会員かを第三者に教えてしまう
パスキーと WalletPublicKey は似たものWalletPublicKey は入場 QR を署名する端末の鍵。1 User に 1 つで、新しい端末で登録すると置き換わる。サインインには使わない端末を替えると古い端末の入場コードが会場で拒否されることを見落とす
トークンはタイマーで早めに更新するもの起動時・前面復帰時・401 のときだけ、1 本ずつ更新するrotation の競合で RefreshTokenInvalid になり、ファンが強制ログアウトされる
パスワードを禁じるにはローカル認証を切ればよいローカル認証 (UserLogin / allowUsernamePassword) はパスキーのサインインも兼ねるので有効のまま。パスワードを設定するページを not-found にし、identity にパスワードを付けないログイン画面に入力欄が出ず、誰もサインインできなくなる
Organizer の Organization でも、未知のメールは隠すべきOrganizer の Organization では未知のメールを「不明」と知らせる設定にしている。ファンの Organization では隠す隠す設定にすると、メールを入力してパスキーでサインインする流れが壊れる (本番で確認済み)
Passkey の提供元名と登録日は、通知が届いたときだけ付く一覧そのものは Zitadel の現状を映す。webhook が 500 を返した通知は Zitadel が再送しないその追加・削除は記録もメールもされない。追加したパスキーは名前だけで日付なしで一覧に出て、本人にはメールが届かない

ほかに、時間の条件が 2 つあります。パスキーの追加と退会には直近 5 分以内のサインインが必要です。そして最後の 1 つのパスキーは削除できません。

11. 退会と削除 ファン Organizer

消すと元に戻せないので、ファンの退会も Organizer の削除も「終わっていないものがあれば消せない」作りです。

ファンの退会

ファンは Settings の退会画面から、確認し、もう一度パスキーでサインインして、自分のアカウントを消せます。次のどれかが残っていると、退会画面にその項目が出て、消す操作は出ません。

  • これから開く公演のチケットを持っている
  • リセールに出品中のチケットがある
  • 抽選の結果待ちの応募がある
  • 支払い中の購入がある

消すときは identity を先に、次に User を消します。消えたあとは、そのパスキーではどのアカウントにも入れません。注文とチケットは記録として残ります。同じメールアドレスで登録し直すと、フォローもチケットも本人確認の結果も無い、新しいアカウントになります。管理者がファンの依頼を受けて消すことも、同じ条件のもとでできます。

Organizer の停止と削除

Organizer は、管理者が 停止 してから 削除 します。停止すると、メンバーはサインインできなくなり、その Organizer が代表していた Artist は別の Organizer に付け替えられるようになります。停止しても Zitadel の Organization は消えません。

削除は、ファイル、Zitadel の Organization、その Organizer の記録をすべて消します。ただし、次のどれかがあると、何も消さずに失敗します (FailedPrecondition)。

  • その Organizer の公演に、返金済みでない注文がある
  • その Organizer の公演に、取り消されていない精算 (Settlement) がある
  • 支払い先口座 (PayoutAccount) の記録がある
