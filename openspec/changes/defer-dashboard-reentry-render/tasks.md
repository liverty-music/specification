## 1. Baseline

- [x] 1.1 Baseline captured on a populated production account (Chrome emulation 412x915, **CPU throttling off**): cold load Rendering 21,352 ms / total 31.6 s; tab-switch re-entry **INP 64,472 ms**, Rendering 24,556 ms within the first 31 s with the interaction still running when recording stopped; **225 date groups**. Supersedes the ~23-group / 2.6 s / INP 2,536 ms figures this change was originally scoped against. Cold-load trace also reported `Forced reflow while executing JavaScript took 58194ms` (see 2.0).
- [x] 1.2 SKIPPED by decision. The fallback ships as the measured MEDIAN (192px; n=225, min 116px, max 579px) rather than the mean. The mean would minimise cumulative scroll-height error slightly better, but `contain-intrinsic-size: auto` remembers each group's real height once rendered, so the literal only applies to groups never yet seen — and with a 116–579px spread no single value is right for most groups anyway. Revisit only if 7.4 shows a restored scroll position landing visibly off.

## 4. Lifecycle — place each concern where it belongs

- [x] 4.1 Keep `loading()` to its synchronous prelude plus `void this.loadData()` (params/query/filter restore, fetch kickoff). Per the capability this is navigation-scoped, earliest, and blocks nothing — it is correct and stays.
- [x] 4.2 Move reflection of render state — including the cache fast path's `dateGroups` assignment and its `timetableLoaded` flip — out of `loading()` and into the component lifecycle (`attached()`), so the component's first render contains only the frame and skeleton. Spike 1: this relocation ALONE produced zero frame-only paints, so it is necessary but not sufficient on its own.
- [x] 4.3 Do NOT add a scheduling primitive. `attaching()` returns nothing; there is no `queueAsyncTask`, `setTimeout(0)` or `scheduler.yield()` anywhere in this change. Spike 1 measured the render block at 44.2 ms for one windowed viewport vs 177.7 ms unwindowed (4x CPU), so containment — not scheduling — is what makes the paint fast. If a future measurement ever shows a yield is needed, use `scheduler.yield()`, not `setTimeout(0)`.
- [x] 4.4 Re-entry restores in a single bounded paint. Do not try to produce a frame-only paint on the cached path: it would cost a frame and flash an empty frame over content the fan has already seen.
- [x] 4.5 Guard the deferred reflection so it never overwrites a fresher background-refresh result that already landed, and cancel it on teardown / a new load so a stale paint never writes into a torn-down or re-navigated route (mirror the existing `abortController` discipline).

## 4b. Reveal motion — DEFERRED to its own change

- [x] 4b.0 Reveal motion is removed from this change. What was built: `@starting-style` plus a `sibling-index()` stagger for first appearance, and a view timeline for scroll reveal. What was measured on the real component: every row began moving at the same millisecond and finished at the same millisecond, while `transition-delay` correctly computed to 0.06s / 0.12s / 0.18s / 0.24s per row. Removing the scroll-driven animation did not change it. Disabling `content-visibility` did not change it. The cause is not known.

  Three explanations were proposed and each was disproved by measurement — that the two mechanisms coexist, that their conflict was the cause, and that containment was the cause. Rather than keep adjusting something whose failure is not understood, the CSS is removed and the work gets its own change, starting from when `@starting-style` actually fires against Aurelia's `repeat` rather than from a fix.

  The card's previous entrance animation stays removed regardless: it fired on every card at once, including ones nobody could see, which is the behaviour this change set out to replace.

- [x] 7.1 Unit-test (`dashboard-route.spec.ts`) that on the cache fast path neither empty state renders before the load settles, the background refresh still fires, `timetableLoaded` still flips (celebration/latch + deep-link intact), and a background refresh that settles BEFORE the deferred reflection is not clobbered by the stale cache. Remove the stale `queueTask` mock — the implementation no longer uses the task queue.
- [x] 7.2 `make lint` + `make test` in `frontend/`, plus `npm run test-storybook` for the rewritten guard and new stories.
- [x] 7.3 `npm run build && npm run verify:build-templates` locally — the dashboard template changes here and a moved marker breaks the production image build, not CI. Update `ROUTE_MARKERS` if needed.
- [x] 7.4 Verified on production (dev is stopped). Confirmed: the frame paints while the fetch is in flight, re-entry INP 140 ms against the 64,472 ms baseline, no empty-state flash, background refresh / celebration / deep-link intact, Settings swaps immediately. Two defects found, fixed in 7.5; a further round found a third, fixed in 7.6. Still outstanding: restoring the scroll position has not been re-verified on production at depth.
  - Beams lit concerts the fan had not scrolled to — every matched card in the timetable at once.
  - The restored scroll position drifted, worse the deeper the fan had gone.
- [x] 7.5 Fix what 7.4 found. Both causes were measured in a spike before anything was changed, and both fixes were measured after.
  - **Beams**: cause was `animation-fill-mode: both`. Before its range a backwards fill holds the `from` keyframe, which is the full-length beam. Measured 37/37 off-screen beams lit at the top of the list, 35/39 and 30/39 further down; with no fill and a `scaleY(0)` base, 0 at every position while on-screen beams are unaffected. The base also covers a card in a skipped group, whose view timeline is inactive so the animation contributes nothing. Guarded by a story that fails (34 beams lit) against the previous declarations.
  - **Scroll**: cause was saving a pixel offset. Off-screen groups are sized from `contain-intrinsic-size` until they render, and the browser's memory of each real height dies with the element — navigation destroys them all, so every group reverts to the estimate and the same pixel value denotes a different place. Measured drift over 225 groups: +8 at depth 20, +20 at 60, +23 at 120, +41 at 180. Three strategies compared at five depths: pixel drifted up to 41 groups, a hand-rolled correction loop missed by 1-3 at every depth (it cannot converge — each correction renders more groups and moves the estimates the next one reads), `scrollIntoView` on the anchored group landed exactly at every depth. Saved state is now the date group at the top edge plus the offset into it.

- [x] 7.6 A second round of production verification found the beams no longer reached their cards. Cause was two mistakes in the same mapping, both measured: the length came from progress over the plain `cover` range, which runs one card-height further than the distance the beam spans; and the box being scaled was viewport-sized while the progress driving it was measured against the scroll area (888px against 748px on the reference layout, an 18.7% slope error on its own). Together: -70px at the top of the screen, +68px at the bottom. Fixed with `animation-range: cover 0% contain 100%` and an overlay bounded to the lane row — 0px at every card at every scroll position, guarded in both directions (reverting either half fails by ~47px). Beams re-verified on production: correct.
  - **CSS anchor positioning was tried and rejected on evidence.** `inset-block-end: anchor(top)` reproduces the length exactly (0px, standalone), but an anchor inside a `content-visibility: auto` subtree is invisible to it: 168/168/313/313/505/505px of error with containment on, 0 across the board with it off. Containment is this change's entire performance win, so the anchor loses. Worth recording so it is not re-attempted.
- [x] 7.7 A claimed third cause — that no view timeline was registering, 0 of 40 — was a measurement error, and the fix built on it has been removed. The count was taken before a single frame had passed; waiting one frame and re-declaring nothing gives the same 18 of 40 live, the 18 being exactly the groups on screen. Two changes had gone in together and the result was credited to the wrong one. The published release notes that stated the wrong cause were corrected. The beams-everywhere symptom is fully explained by the fill mode in 7.5; there was no second cause.
- [x] 7.8 Close the gap the two scroll defects exposed: the tests mocked the DOM and so could not see what actually went wrong. A component test now scrolls a screen at a time so the groups passed through really render, empties and refills the timetable so every group is rebuilt with its estimate restored — what navigation does — and asserts the fan gets back the DATE they left on. Group heights in the fixture are uneven on purpose; an even list would let a broken implementation pass. Restoring by pixel offset instead fails it: left on 2026-09-13, returned to 2026-09-16, in a list of only thirty.

## 8. Close-out

- [ ] 8.1 Sync both deltas into the main specs (`openspec sync`) before archiving. `dashboard-timetable-rendering` does not yet exist under `openspec/specs/` — it is created by the sibling `optimize-dashboard-render-cost` change, so that change must sync first or the two deltas must be reconciled at sync time.
- [x] 8.2 PR descriptions record the measured baseline (cold load 21,352 ms Rendering / 31.6 s total; re-entry INP 64,472 ms, 225 date groups, CPU throttling off) and the spike evidence behind each decision. The after-figures are still outstanding — see 7.4. frontend#614 merged as 0e5cfe5; specification#966 merged as 3951aeb.
- [x] 8.3 Handed off to `progressive-route-rendering`. What the final shape actually was:
  - **Reflection runs from `attached()`**, guarded so a background refresh that already landed is never overwritten by the stale cache. The relocation alone produces no earlier paint — measured — so it stands on the non-blocking contract, not on a paint argument.
  - **Nothing schedules a paint.** `queueAsyncTask`, and later yielding from `attaching()`, were both dropped: once containment bounds the render to the viewport a single paint is fast (177.7 ms → 44.2 ms at 4x CPU for one windowed viewport), and forcing a frame-only paint on re-entry would cost a frame and flash an empty frame over content the fan has already seen.
  - **Scroll save/restore** is `unloading` → store → `attached()` after reflection, and it moved out of the route entirely: the route reached into the child's DOM at first, which failed the moment a spec used a real DI container. It is now `ConcertHighway.scrollAnchor`, living next to the scroll container it reads. Any route generalising this should expose it from whichever component owns the scroller, not query for it — **and must not save a pixel offset**. Under viewport-scoped rendering an offset denotes a different place after navigation than before it (7.5 measured up to 41 groups of drift), because the browser's memory of each real height dies with the elements. Save what the position identifies — here the date group — and restore with `scrollIntoView`, which was the only strategy of three that landed exactly.
  - **The skeleton is the component's own structure**, not a generic placeholder — that is what makes the swap layout-shift-free, and it does not transfer to a route whose list has a different shape. A generalised version has to let each surface shape its own.
  - **Reveal motion did NOT ship and is not transferable.** `@starting-style` + `sibling-index()` for first appearance and a view timeline for scroll reveal were built, measured, and removed: every row moved together despite correctly staggered delays, and the cause is unknown. See 4b.0 for the measurements. A route generalising this must treat reveal as unsolved and start from the investigation, not from this CSS.
  - **Presentation stays in CSS**: per-element dynamic values go through custom attributes (`beam-vars`, `beam-timeline`), because templates may not carry `style`. Any generalisation must respect that.
  - **Containment and per-element CSS references do not mix.** An element inside a `content-visibility: auto` subtree cannot serve as a CSS anchor — measured, and the reason anchor positioning was rejected here despite being exact. Anything that has to point at a contained element from outside it needs checking against containment before it is designed around.
  - **Two changes at once means neither is measured.** The one wrong conclusion in this change came from introducing a wait and a re-declaration together and crediting the result to the re-declaration; separating them showed the wait alone accounted for it. Every other conclusion here was reached by reverting the fix and confirming the guard fails.
  - **`verify-route-loading`** already enforces the non-blocking half app-wide and can be tightened to require the declarative form once routes move over.
