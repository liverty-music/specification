## Context

See proposal.md. Facts (backend `origin/main`, 2026-11-26):

- `userUseCase.Delete` runs `User.SerializeDeletion` around the blocker check, `DeleteIdentity` and `User.Delete`, in the fan API or the admin console API process.
- Durable workflows (DBOS, change `introduce-durable-workflows`): `Workflows.Start` and `Await` for callers; the workflow worker runs them, resumes them after a restart, retries a step that fails with Unavailable or DeadlineExceeded, and reports workflows that end in a failed state to an admin (`workflow.needs_admin`). The fan API and the admin console API already have the `dbos` grants.
- The identity service's listener on port 9100 (`di.EventConsumerProcedures`) is reached only by the workflow worker (NetworkPolicy `identity-ingress`, `IDENTITY_SERVICE_URL`), which runs as the fan API's service account.
- The worker's `UserUseCase` is built without the identity remover and the blocker reads.

## Goals / Non-Goals

**Goals:** a deletion that was accepted always ends in removal or in an admin being told.

**Non-Goals:** repairing Users already left behind (there are none to repair: an admin can delete one on the Users screen); any screen change.

## Decisions

- **A workflow `delete-user`, awaited by Delete.** Delete does its two checks, starts the workflow and awaits it for 5 seconds. The fan and admin apps give up on a call after 10 seconds (`rpcTimeoutMs`, its default, which prod does not override), counted from before the request is sent, so the wait leaves room for the network and the checks before it; it is also below the API handler timeout. A timeout of the await is success: the run is durable. Alternatives: answer Unavailable on a timeout, rejected because a fan whose identity is gone cannot sign in again to retry, and the withdrawal screen would report a failure for a deletion that completes; repair at the next sign-up, which leaves personal data until then and lets a sign-up delete another User; a sweeper over Users without an identity, a second mechanism the workflow change replaced.
- **The User first, then the identity.** `remove-user`, under `SerializeDeletion`: identity removal not configured → Internal, nothing removed; User gone → done; blockers → FailedPrecondition; `User.Delete`. `remove-identity`, without a lock: `DeleteIdentity`. The record removal is the point of no return and a local transaction; everything after it is an idempotent external call that nothing can block, because every create of a blocker needs the User. No lock or transaction is held across the call to the identity provider (PostgreSQL 13.3.4: "it is a bad idea for applications to hold transactions open for long periods of time"). Reading the User first matters: the blocker read fails with NotFound for a removed User. The workflow input carries the provider user id read by Delete, so the second step needs no User. Alternatives: the identity first, in two steps, rejected because a create waiting on the lock gets it between the steps, even when nothing fails, and leaves a fan who cannot sign in with a User that cannot be removed; both removals in one step under one lock, rejected because it holds a transaction and a connection across the external call and can still end with the identity gone and the User kept.
- **A removed identity gets no new User.** Until `DeleteIdentity` succeeds the identity can sign in, and the fan app calls `Create` whenever `Get` answers NotFound, so a new User would take the email and be orphaned by the second step. `User.Delete` records the provider user id in a new table `deleted_user_identities` (`provider_user_id TEXT PRIMARY KEY`) in the same statement as the delete (a data-modifying CTE), and `User.Create` refuses a recorded id with FailedPrecondition. `Create` checks after inserting the User, in the same READ COMMITTED transaction: an insert that meets the uncommitted delete of the same provider user id waits for it on the unique index, so the check then sees the record; no further lock is needed. The record is kept: the id is opaque, the identity provider does not reuse it, and a token issued before the removal outlives it. Alternative: let the second step delete a User created meanwhile; rejected because that User can already hold a blocker.
- **Rows locked.** As today: `pg_advisory_xact_lock('user:' || id)` exclusive in `remove-user`, shared in every path that creates a blocker (`delete-fan-accounts` design D2).
- **Every failure ends the run in ERROR**, a blocker included, so the existing report tells an admin. The awaiting Delete returns that error's code while the User remains; once the User is gone (it reads the User after a failed run) it succeeds, since the account is deleted and the fan cannot retry. An admin finishes a run that left the User by deleting it on the Users screen once the cause is gone, and a run that left only the identity with the `workflow-needs-admin` runbook (resume or fork).
- **Workflow id `delete-user:<user id>:<new uuid>`.** A fixed id per User would return an earlier failed run and never try again. Concurrent runs serialize on the lock.
- **A failed run keeps its error code.** DBOS v1.9.0 stores a workflow's error with gob and, when the type cannot be encoded, as its message only. An `apperr` error cannot be encoded (`type not registered for interface: apperr.AppErr`), so a caller in another process would read every failure as Internal. `internal/infrastructure/workflow` records the failure of a run in a form that carries the apperr code and message, and `Await` returns an error with that code. This holds for every workflow, so `Await` also marks an error as the run's own failure, which keeps it apart from the caller's wait timing out. The passkey removal's wait for the addition's run branches on Unavailable, DeadlineExceeded and Aborted as outcomes of the wait; it checks the mark first and keeps treating every failed run as one that stores nothing. `OrderUseCase.Place` returns a failed Issue run's code where it returned Internal. Alternative: end the run successfully with the code in its result; rejected because the admin report only sees failed states.
- **Deadline 24 hours**, as the other workflows that retry an external call.
- **Retry classification.** `IdentityRemover.DeleteIdentity` maps an unreachable provider to Unavailable instead of Internal. `rdb.toAppErr` today classifies only PostgreSQL error codes and leaves a failed connection (`pgconn.ConnectError`, a network error) unclassified; it maps those to Unavailable too, which covers `User.Delete`, the lock and the blocker reads. Without this the step would not retry a database outage.
- **Permission moves to the worker.** `DeleteIdentity` joins the port 9100 list and leaves the fan and admin console API lists. The worker also processes external data (concert discovery), which the identity spec wanted kept away from identity deletion; this is accepted so that the removal can be retried. The two internet-facing APIs lose the permission. Alternative: retry only the record removal in the worker; rejected because the identity removal, the step that now runs last, is the one that needs the retry. Rename `EventConsumerProcedures` to `WorkflowWorkerProcedures`.

## Risks / Trade-offs

- [The identity can sign in while the identity provider call keeps failing] → no account can be created for it; signing up again with the same email waits until the identity is removed, and an admin is told after a permanent failure or 24 hours.
- [A run left only the identity] → the User is no longer on the Users screen; the admin resolves the run itself.
- [During the rollout an old API pod calls DeleteIdentity and is refused, or a new API starts a workflow the old worker does not know] → the first fails that one request, which the person retries; the second waits in the queue until the new worker runs.
- [During the rollout an old fan API pod creates a User for a recorded id] → needs a deletion and a sign-up of the same identity within the rollout; an admin can delete that User.

## Migration Plan

The migration adds `deleted_user_identities` with the grants the fan API's database role needs (the worker runs as that role); it applies on merge, before the release is pinned, and the old code ignores it. One backend release for identity, worker and APIs. Rollback: revert the backend release and keep the table. A `delete-user` run left pending or enqueued is not in the admin report (only failed states are), so before reverting, check that none is open (`dbos` system tables, read-only), or resolve those runs afterwards.
