## Context

`backend#468`: no production code ever creates a `Settlement` row, so `ReleaseDueSettlements`'s `ListHeld` scan is always empty and Organizers are never paid out. The issue's suggested fix offered two options: (A) create the Settlement inside the issuance transaction, or (B) have the sweeper backfill it for issued Orders without one. See proposal.md for the chosen direction (A) and its capability deltas.

## Decisions

- **Settlement creation lives in `Order.Issue`, not a separate sweep.** `IssuanceRepository.Issue` already opens one pgx transaction for the Order and its Tickets; adding the Settlement (and its one split) to that same transaction means an issued Order can never end up without its Settlement — no second pass, no window where `ListHeld` misses a row. This also matches the entity spec's Settlement.organizer/event/splits being required at creation, not backfilled.
- **`PayoutSweeperUseCase.EnsureSettlementExists` and `Settlement.Upsert` are removed, not kept as a defensive backfill.** Nothing in production ever called either (confirmed by the issue and by `grep`), so keeping them would leave dead interface surface with no caller and no test coverage pulling its weight. If a genuine backfill need surfaces later (e.g. a bug reintroduces the gap, or pre-fix Orders need reconciling), it is cheaper to add a purpose-built one-shot script against `SettlementRepository` than to keep an unused, easily-bitrotting usecase method alive today.
- **Organizer resolution (`Event.GetOrganizerID`) is a plain read before the transaction, not part of it.** It walks `event -> series -> organizer_id`, mirroring the existing `Event.GetEventStartTime` minimal-repository pattern (`internal/infrastructure/database/rdb/event_start_time_repo.go`). A read-then-write race (the event's series changing organizer between the read and the Issue transaction) is not a real concern: series ownership is not reassigned in the product today.
- **Failure mode: `GetOrganizerID` returning NotFound fails the whole issuance** (no Order, no Tickets, no Settlement) rather than silently issuing without a Settlement. A lottery phase can only be authored on an organizer-owned (first-party) series today, so a Won-captured application whose event has no Organizer indicates a data-integrity problem, not a normal business path. Failing closed preserves the invariant this change exists to establish — "every issued Order has a Held Settlement" — instead of reintroducing a narrower version of #468 for that one event.
- **Platform fee stays at the existing `TODO(threshold)` placeholder (effectively 0): the Organizer's split is the Order's full amount.** The fee rate is an explicit, separate business decision tracked at `backend#778` ("Fee rate + buyer-pass-through") and was already deferred with this exact wording in the `ensure-settlement-exists` spec this change removes. This change does not guess at a rate; it carries the placeholder forward unchanged.

## Risks / Trade-offs

- [No automated backfill for any Order issued before this change ships] → Not a real risk in practice: per the issue, no Settlement has ever been created by any code path, so there is nothing to reconcile beyond what a future targeted script could handle if it turns out any such Orders exist in an environment that matters.
- [`Event.GetOrganizerID` failing closed blocks issuance for a mis-owned event] → Acceptable: this can only happen if a lottery phase was created on a non-organizer-owned series, which today requires no such path to exist in the product; if it ever does, failing loudly at issuance is safer than an Order with no payout destination.
